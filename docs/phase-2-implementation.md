# Phase 2 — implementation and verification guide

Everything needed to finish, apply, and verify phase 2. Written to be handed to
Cursor (or executed by hand) without re-reading the design conversation.

---

## 0. What phase 2 is

In production, a trainee who finishes phase 1 moves on to **live production
cases**: they work a real case, send it to the trainer, and the trainer sends
corrections back. The current trainees will not get production access, so phase
2 is **simulated** with 30 fixed cases whose source material is preloaded.

Confirmed rules:

| Rule | Value |
| --- | --- |
| Cases | 30, identical for every trainee |
| Release | 5 per **working day**, over 6 days |
| Due date | the **next working day** after release, at the latest |
| Deliverables | same as phase 1 — PDF 1, PDF 2, OV, as OneDrive links, generated by the trainee |
| Preloaded material | the case *source* files, as OneDrive links |
| Start | **automatic**, once all 32 phase-1 cases are `approved` |
| Journey categories | none |
| Order numbers | real VIP numbers, **not yet supplied** |

**"Cycle" means the review cycle** — `submitted → in_review → corrections_sent →
awaiting_resubmission → approved` — not batching and not one-case-at-a-time. A
trainee may have several phase-2 cases open at once. There is no sequential
gate, so no gating code should be written.

**Bug found and fixed 2026-08-23: pre-existing fully-approved trainees never
entered phase 2.** `on_case_approved_start_phase_2` only fires on a fresh
transition *into* `approved` (`when (new.status = 'approved' and old.status is
distinct from new.status)`). Two real Dev trainees — AARON FONG and Max
Pentecost — had all 32 phase-1 cases approved **before** migration
`20260823140000` (and its trigger) existed, so applying the trigger never
retroactively fired for them; they were silently stuck outside phase 2 despite
satisfying the rule. `20260823160000_phase_2_backfill_completed_trainees.sql`
runs the trigger's own qualifying check once against existing data and calls
the same idempotent `private.start_phase_2()` — safe to re-run, and a no-op on
an environment (e.g. Prod, later) where the trigger already caught everyone.
Applied to Dev: both trainees now show `phase_2_started_on = 2026-08-23` with
30 phase-2 cases each.

**Second, more serious bug found the same day: phase-2 cases were invisible
to trainees even after release.** `start_phase_2()` created cases with the
default status, `not_started`. `not_started` is **trainer-owned**
(`TRAINER_OWNED_STATUSES`, `metrics.py`) — in phase 1 it means "the trainer
hasn't clicked Assign case yet," and a trainee never sees a `not_started`
case in "needs you" or as their next case; the dashboard shows "Waiting for
assignment." Phase 2 has no assignment step by design (release is the
trigger), so every one of the 30 cases was structurally stuck: even once
released, a trainee would see nothing, and the trainer would have had to
click "Assign case" 30 times per trainee — exactly the manual work "automatic"
was meant to replace. Real trainees (AARON FONG, Max Pentecost) hit this and
reported "I don't see any new cases."
`20260823170000_phase_2_cases_start_assigned.sql` makes `start_phase_2()`
create cases as `'assigned'` (trainee-owned from the moment they release) and
backfills the 60 cases already created for these two trainees. Verified
end-to-end against real Dev data (see §5.4 below) that a released, `assigned`
phase-2 case now surfaces correctly as the trainee's next case.

**Also added: a trainee dashboard "all caught up" state.** Previously, once a
trainee had nothing in "needs you" (e.g. all 32 phase-1 cases approved, phase
2 not released yet), the dashboard fell back to showing *some* approved case
as "Next up" — confusing, and indistinguishable from having real work to do.
`views/trainee.py` now branches on whether anything is actually actionable:
nothing at all → the existing "No cases yet" state; cases exist but none need
the trainee and phase 2 has started → a "🎉 Phase 1 complete — you're in Live
cases now" card, naming the date the next batch unlocks if any are still
pending; cases are with the trainer for review → "N cases in review"; anything
actionable → the existing next-up card, unchanged.

**Correction 2026-08-23, same day: the auto-assign fix above was wrong.**
The trainer clarified the actual model: only case *creation* and the
release/pacing schedule are automatic. **Assignment stays manual, one case at
a time, exactly like phase 1** — the 30 phase-2 cases sit in the trainer's
inbox as `not_started` ("needs assignment") and a trainee sees only what the
trainer has explicitly clicked "Assign case" on.
`20260823180000_phase_2_cases_stay_unassigned.sql` reverts
`start_phase_2()` to the phase-1 pattern (status defaults to `not_started`,
not specified in the insert) and reverts the 60 rows the previous migration
touched. `released_on`/`due_date` keep their meaning as the trainer's
*suggested* pacing — the same role `schedule_due_date` already plays in phase
1's "Assign case" form — not a visibility mechanism.

Two more corrections in the same pass, both in `views/trainee.py`:
- Dropped `released_only=True` from the trainee's case fetch (and the
  matching filter in `app_pages/trainee_questions.py`) — visibility is
  status-driven only, so a date filter on top of it was redundant at best and
  wrong at worst (it would have hidden a case the trainer explicitly assigned
  early, before its suggested release date).
- Removed the "not released yet" guard in the case workspace, and reworded
  the "all caught up" congratulations card to never quote a specific release
  date — assignment timing is the trainer's call, not a schedule the app can
  promise on their behalf.

Re-verified end to end with real Dev data after the revert: the trainee's
frame now correctly shows 0 actionable cases (all 30 sit `not_started`,
trainer-owned) while the trainer's Cases inbox correctly shows all 30 as
"needs you" — matching "el resto están en mi inbox hasta cuando yo los
asigno" exactly.

**Collateral damage from the revert, caught immediately: the blanket revert
clobbered real assignments.** Between the auto-assign bug and its revert, the
trainer had already assigned 5 real cases each to AARON FONG and Max
Pentecost through the actual UI — each had a genuine, open
`homework_assignments` row (`status = 'sent'`, a real due date). The revert's
`update cases set status = 'not_started' where phase_no = 2 and status =
'assigned'` didn't exempt those 10 — it doesn't know the difference between
"assigned by my bug" and "assigned for real," so it knocked their case status
back to `not_started` while their `homework_assignments` rows stayed. The
trainer's inbox then showed all 30 as needing assignment again; clicking
"Assign case" on one of the 10 hit `one_open_homework_per_case_idx` — an open
assignment already existed for that case.
`20260823190000_phase_2_case_status_matches_homework.sql` treats
`homework_assignments` as the source of truth (which is exactly what that
unique index means: at most one open assignment per case) and restores
`cases.status = 'assigned'` for any case with an open assignment row left at
`not_started` — a no-op everywhere this specific inconsistency doesn't exist,
so safe to replay on Prod later. Verified on Dev: AARON FONG and Max
Pentecost each show 5 `assigned` (with their real due dates intact) + 25
`not_started`, and there is no longer any case anywhere with an open
homework assignment sitting at `not_started`.

### What the migration does

1. Adds `phase_no` (1|2) to `cases` and `case_schedule_template`; the template
   PK becomes `(phase_no, set_no, case_no)`, and `cases` gets
   `unique (trainee_id, phase_no, set_no, case_no)`.
2. Raises the `case_no` checks from `1..16` to `1..30`.
3. Makes `order_number` and `journey_category` nullable on both tables.
4. Adds `cases.released_on` and `trainees.phase_2_started_on`.
5. Inserts 30 template rows: `phase_no = 2`, `set_no = 1`, `case_no` 1–30,
   `catalog_label` `L01`–`L30`, `training_day` 1–6 (five per day).
6. Rewrites `private.create_trainee_cases()` to insert `phase_no = 1` only, so
   new trainees still start with exactly 32 cases.
7. Adds `private.start_phase_2(trainee_id, anchor)` — idempotent; creates the
   30 cases, stamps `phase_2_started_on`, logs a `phase_2_started` event.
8. Adds trigger `on_case_approved_start_phase_2` on `cases`, which calls
   `start_phase_2` once the last phase-1 case is approved.
9. Rebuilds the `trainee_progress` view with per-phase counters; unreleased
   phase-2 cases never count as overdue or as waiting on the trainee.

**Phase-2 `training_day` means something different from phase 1.** In phase 1 it
is the offset in working days from `trainees.start_date`. In phase 2 it is the
offset from `trainees.phase_2_started_on`. Same column, two anchors.

## 2. Pre-flight — run this BEFORE applying

The migration drops constraints by name. If PostgreSQL named them differently in
your project, `drop constraint if exists` silently does nothing, the old
restrictive check survives, and **inserting `case_no > 16` fails at runtime**
rather than at migration time. Verify the names first.

```sql
select conrelid::regclass as table_name,
       conname,
       pg_get_constraintdef(oid) as definition
from pg_constraint
where conrelid in (
  'public.cases'::regclass,
  'public.case_schedule_template'::regclass
)
order by conrelid::regclass::text, conname;
```

The migration assumes these four exist:

| Constraint | Expected definition |
| --- | --- |
| `cases_case_no_check` | `CHECK (case_no >= 1 AND case_no <= 16)` |
| `cases_trainee_id_set_no_case_no_key` | `UNIQUE (trainee_id, set_no, case_no)` |
| `case_schedule_template_pkey` | `PRIMARY KEY (set_no, case_no)` |
| `case_schedule_template_case_no_check` | `CHECK (case_no >= 1 AND case_no <= 16)` |

**If any name differs, edit the migration to use the real name before running
it.** Do not skip this step.

Record the starting state so you can compare afterwards:

```sql
select
  (select count(*) from public.case_schedule_template)      as template_rows,
  (select count(*) from public.cases)                        as cases,
  (select count(*) from public.file_requirements)            as file_requirements,
  (select count(*) from public.trainees where active)        as active_trainees;
```

## 7. Remaining work

### 7.1 Case catalog — ready to apply

`supabase/migrations/20260823150000_phase_2_case_catalog.sql` carries the real
catalog. Apply it the same way as the first migration (inside `begin/commit`).

It adds four things:

| Column | Table | Meaning |
| --- | --- | --- |
| `order_number` | both | The training case the trainee opens in VIP (`12-26-07-…`) |
| `source_order_number` | both | The production case it mirrors (`12-26-05/06-…`), trainer reference only |
| `journey_category` | both | `Success` (25 cases) or `Manual` (5 cases) |
| `instruction` | both | Mandatory per-case instruction, or null |

Five cases — L06, L12, L18, L24, L30, every sixth — carry **"Reject and plan
manually for practice"**. Three more — L16, L22, L23 — carry **"Plan only"**.
The other 22 have no instruction.

The instruction is a **column on the case**, not a `case_resources` note, so
that the case header can render it as a callout. Resources render inside a
collapsed expander labelled "suggested", which is far too quiet for a step the
trainee must not miss.

`journey_category` was left null by the first migration on the assumption that
phase 2 had no categories. The matrix supplies Success/Manual, which is exactly
that column's meaning, so it is reused rather than adding a `case_type` column.

### 7.2 Preloaded case material — needs a code change, not just data

The preloaded OneDrive links belong in `case_resources`
(`resource_type = 'link'`, `created_by = 'system'`), which already exists with
RLS. Two things block it:

1. **`resource_rules.py` cannot target a phase.** `_matches()` supports
   `set_no`, `case_no_range` and `section` only. Add `phase_no` to the match
   vocabulary, or phase-2 rules will also fire on phase-1 cases 1–16.
2. **The existing call site never sees phase-2 cases.** `views/trainer.py:293`
   calls `build_system_resources(repository.list_cases(trainee_id))` right after
   creating a trainee. Phase-2 cases do not exist at that moment — they are
   created later by the database trigger, so no resources are ever attached to
   them.

Pick one of two fixes:

- **App-side (preferred).** After `start_phase_2` has run, call
  `build_system_resources(repository.list_cases(trainee_id, phase_no=2))` and
  `add_case_resources(...)`. Trigger it when the trainer first opens a trainee
  whose `phase_2_started_on` is set but which has no phase-2 resources yet.
  Keeps the link catalogue in Python where it is reviewable.
- **SQL-side.** Insert the resources inside `private.start_phase_2` from a new
  template table. Atomic with case creation, but splits the resource catalogue
  across two languages.

### 7.3 UI — done for this pass

**Trainee-facing:**

- `views/trainee.py` — the portal fetches with `released_only=True`; the case
  workspace re-checks `released_on` server-side so a stale link or a typed URL
  can't open a phase-2 case before its release day either.
- `app_pages/trainee_questions.py` — same `released_only=True` guard on its
  case list.
- The mandatory per-case `instruction` ("Reject and plan manually for
  practice", "Plan only") renders as a `st.warning` in the case header
  (`components/ui.py`), both the full header and the trainer's compact review
  header — impossible to miss, distinct from the optional trainer note below
  it.
- The progress journey (`components/progress_journey.py`) is a phase-1 Set
  1/2 map; `trainee.py` now explicitly filters to phase-1 cases before
  passing them in, rather than relying on the component's incidental
  `case_no <= 16` filter. **A phase-2 equivalent visual was not built** — see
  the gap noted below.

**Trainer-facing:**

- `views/trainer.py` inbox (`_render_cases_inbox`) gets a **Phase 1 / Live
  cases** segmented control, shown only for trainees who have reached phase 2.
  `views/case_board.py`'s `select_case_from_list` takes a `phase_no` param:
  phase 1 keeps its Set 1/2 toggle unchanged, phase 2 is a flat list with no
  Set toggle (phase-2 cases all carry `set_no = 1`, so without this gate they
  would have silently merged into "Set 1" alongside phase-1 cases 1–16).
  Wording ("5 in set" vs "5 released") adapts to the phase shown.
- The kanban board (`views/kanban.py`, the trainer's default landing view)
  already pooled every case regardless of phase — no phase filter was needed
  there. Its card caption only needed a fix: `Set {N}` is meaningless for a
  live case, so it now reads `Live case` instead.
- `case_labels.case_label()` and `case_title()` are phase-aware everywhere
  they're already called: `Live case L06 · 12-26-07-0005` instead of
  `Case L06`. This fixed a case-label leak in `views/metrics.py`'s analytics
  tables too (`hardest_cases`, recurring issues), which would otherwise have
  shown `Set 1 · Case L06` for a live case.
- The bulk due-date panel's catalog-label derivation
  (`card.case_label.removeprefix("Case ")`) is phase-aware now too, so it
  doesn't leave `Live case ` stuck on the front of the label for phase-2 cards.

**Gap — no phase-2 equivalent of the journey visual.** Trainees in phase 2 see
their live cases in the next-up card, the coming-up list, and the case
workspace, but not in a single visual map the way phase-1 Set 1/2 are mapped
today. Building one (a flat 30-case strip, most naturally) is a separate,
larger design task and was intentionally left out of this pass.

**Not done in this pass — §7.2 still applies as written below.** The
preloaded-material resources still are not attached to phase-2 cases; that
needs the `resource_rules.py` phase-matching fix and a new call site once the
OneDrive links are supplied.
